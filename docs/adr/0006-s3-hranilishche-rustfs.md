# ADR 0006. S3-хранилище картинок: aioboto3, presigned-ссылки, RustFS в dev

**Статус:** принято (этап 3)

## Решение
- Клиент S3 `aioboto3` создаётся в `lifespan` (как остальные ресурсы). Два клиента: рабочий (внутренний адрес)
  и подписывающий (публичный адрес для браузера; подпись считается локально, в сеть он не ходит).
- Бакет приватный. Картинка отдаётся временной presigned-ссылкой (1 час), в БД хранится только ключ объекта.
- Загрузка `PUT /catalog/injectors/{id}/image` только для admin: проверяются тип (JPEG, PNG, WebP), «магические байты»
  файла (заявленному `Content-Type` доверять нельзя) и размер (до 2 МБ, читается на 1 байт больше лимита).
- Сначала файл в S3, потом запись в БД и сброс кэша, затем удаление старого файла. Сбой на любом шаге не оставляет
  в БД ссылку на несуществующий файл.
- В dev S3 эмулирует **RustFS**.

## Почему RustFS, а не MinIO
Официальные образы MinIO сняты с публикации (`minio/minio` на Docker Hub не существует, quay.io требует авторизации).
RustFS: лицензия Apache 2.0, тот же S3 API, веб-консоль, активно обновляется (образ `rustfs/rustfs:1.0.4`).
Код приложения про конкретное хранилище не знает (только `ImageStorage`), поэтому замена обратима: в prod можно
использовать AWS S3 или любое S3-совместимое хранилище, поменяв адрес и ключи.

## Почему presigned, а не проксирование через api
Файлы не проходят через процесс `api` (нет нагрузки на него и на его память), а доступ всё равно ограничен по времени.
Цена: адрес хранилища должен быть доступен браузеру (`S3_PUBLIC_ENDPOINT_URL`), а в dev это порт 9000 на localhost.

## Нюансы, найденные при реализации
- Первое создание клиента botocore читает описания S3-API с диска (на медленной файловой системе до 10 с), поэтому
  `aioboto3.Session` создаётся один раз на процесс.
- Ключи доступа RustFS берутся из файлов секретов: образ `*_FILE` не читает, поэтому `entrypoint` экспортирует их
  в переменные окружения внутри контейнера.
