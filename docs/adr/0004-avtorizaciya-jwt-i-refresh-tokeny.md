# ADR 0004. Авторизация: короткий JWT + ротируемые refresh-токены в БД

**Статус:** принято (этап 2)

## Решение
- **Пароли:** Argon2id (`argon2-cffi`), хэширование в потоке (`asyncio.to_thread`), пересчёт хэша при входе,
  если параметры устарели. Пароль 8–128 символов.
- **Access-токен:** JWT HS256, 15 минут, claims `sub`, `role`, `type=access`, `iat`, `exp`, `jti`. Алгоритм при проверке
  задан явно (защита от `alg=none`). Секрет в файле `jwt_secret` (не короче 32 символов).
- **Refresh-токен:** случайные 256 бит, клиенту отдаётся как есть, в БД только SHA-256. Каждое использование
  выдаёт новый токен, старый отзывается. Токены одной цепочки входа образуют семью (`family_id`).
- **Повторное использование** отозванного токена отзывает всю семью (кража или рассинхронизация клиента).
  Гонку двух одновременных запросов решает условный `UPDATE ... WHERE revoked_at IS NULL`.
- **Роль и блокировка** берутся из БД на каждый запрос, а не из токена, поэтому действуют сразу.
- **Rate limiting** (Redis, счётчик с TTL через Lua): регистрация по IP; вход по IP и по email (только неудачи).
  Redis недоступен: запросы пропускаются (fail-open), потому что Redis не источник истины.
- **Утечки:** одинаковый ответ и одинаковое время для «нет такого email» и «неверный пароль»
  (проверка против фиктивного хэша). Email в логи не пишется.

## Почему не иначе
- **Только JWT без refresh в БД:** выход из системы и отзыв невозможны до истечения токена.
- **Сессии вместо JWT в `api`:** сессии мы уже храним на стороне `web` (BFF, Redis). `api` остаётся без состояния
  и пригодным для других клиентов (мобильное приложение).
- **Refresh в Redis:** потеря Redis разлогинила бы всех, а требование проекта: Redis не источник истины.
- **Argon2 для refresh-токена:** не нужен, у токена высокая энтропия, а быстрый хэш даёт поиск по индексу.

## Компромиссы
- Дубль email возвращает 409, то есть позволяет проверить, зарегистрирован ли адрес. Для магазина это привычный
  компромисс удобства; от перебора защищает лимит регистраций по IP.
- Реальный IP клиента за nginx появится после настройки доверенных прокси (этап 12): до этого лимит по IP считается
  по адресу прокси.
