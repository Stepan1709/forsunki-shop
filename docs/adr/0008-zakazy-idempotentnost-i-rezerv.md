# ADR 0008. Заказы: резерв остатков, идемпотентность, машина состояний

**Статус:** принято (этап 5)

## Решение
- **Оформление `POST /orders`** одной транзакцией: условный `UPDATE injectors SET stock = stock - :n WHERE id = :id AND
  stock >= :n AND is_active RETURNING цена`, создание заказа `PENDING_PAYMENT`, очистка корзины, событие `order.created`
  в outbox. Нехватка любой позиции откатывает всё: частичных заказов не бывает. Позиции резервируются в порядке `id`,
  чтобы транзакции не блокировали друг друга по кругу (deadlock).
- **Цена фиксируется снимком** в `order_items` в момент резерва (берётся из `RETURNING` того же UPDATE). Корзина всегда
  показывает текущую цену каталога, оформленный заказ её не меняет.
- **Идемпотентность HTTP.** Заголовок `Idempotency-Key` обязателен для `POST /orders` и `POST /orders/{id}/cancel`.
  Ключ хранится в таблице `idempotency_keys` с `PRIMARY KEY (user_id, key)`; вставка ключа, действие и сохранение ответа
  в одной транзакции. Повтор возвращает сохранённый ответ с заголовком `Idempotent-Replayed: true`; тот же ключ с другим
  запросом даёт 422. Одновременные повторы ждут друг друга на уникальном индексе. Неудачные попытки (409 и т.п.) не
  запоминаются: после исправления причины тот же ключ можно использовать снова.
- **Машина состояний** (`orders/state.py`): `PENDING_PAYMENT → PAID | PAYMENT_FAILED | CANCELLED | EXPIRED`, остальные
  статусы конечные. Смена статуса только условным `UPDATE ... WHERE status IN (источники)`; остатки возвращаются только
  тем, кто реально сменил статус (отмена, истечение, отказ платежа). Повтор того же перехода безопасен, обратный или
  недопустимый переход даёт 409.
- **Защита от IDOR:** запросы к заказу фильтруются по `user_id`; чужой заказ неотличим от несуществующего (404, не 403).
- **Корзина** хранится в Postgres (данные пользователя, не кэш); `PUT` устанавливает количество (идемпотентно само по себе).

## Почему идемпотентность не добавлена к `/auth/*`
Вход и refresh вернули бы клиенту токены из таблицы: хранить в БД ответы с токенами небезопасно. Регистрация и так
идемпотентна естественно (`UNIQUE(email)` -> 409), выход тоже (отзыв уже отозванного не ошибка). Механизм
(`run_idempotent`, `get_idempotency_key`) универсален и будет подключён к `POST /repair-requests` (этап 7) и платёжным
операциям (этап 6). Отдельные события и webhook'и дедуплицируются по `message_id` (inbox) и `provider_event_id`.

## Усиление outbox
Событие без получателя (нет очереди; `order.created` появится в этапе 6) раньше останавливало бы весь relay: `mandatory`
возвращал сообщение, и пачка прерывалась. Теперь возврат сообщения (`Unroutable`) откладывает только эту строку
(`attempts`, `next_attempt_at` с экспоненциальной паузой до часа, `last_error`), а остальные события уходят. Поломка
самого брокера по-прежнему останавливает пачку.

## Компромиссы
- Наличие в каталоге приблизительное: заказы часто меняют остаток, поэтому весь кэш каталога по ним не сбрасывается
  (цена такого решения: карточка может показывать устаревший остаток до TTL). Источник истины при заказе: условный UPDATE.
- Ключи идемпотентности и устаревшие записи пока не чистятся (запланировано вместе с чисткой outbox/inbox, этап 11).
- Корзина только у вошедшего пользователя (гостевой нет): проще и безопаснее на текущем этапе.
