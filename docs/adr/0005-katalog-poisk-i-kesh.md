# ADR 0005. Каталог: поиск, пагинация и кэш Redis

**Статус:** принято (этап 3)

## Решение
- **Поиск в Postgres:** расширение `pg_trgm` и GIN-индексы по `injectors.oem_normalized` и `engines.name`
  (поиск подстроки `LIKE '%...%'`). Артикул ищется по нормализованному виду без пробелов и дефисов:
  `0 445-110 183` находит `0445110183`. Спецсимволы `%` и `_` из запроса экранируются.
- **Пагинация keyset (курсор):** `WHERE id > :last ORDER BY id LIMIT n+1`. Курсор непрозрачный (base64 от id).
  Лишняя запись сверх лимита показывает, что страница не последняя, и `COUNT(*)` не нужен.
- **Кэш cache-aside:** ключи содержат версию каталога (`cat:v7:...`). Любое изменение товара увеличивает версию
  (`INCR`), старые ключи перестают читаться и истекают по TTL. TTL с разбросом ±10%.
- **Cache stampede:** первый запрос берёт блокировку `SET NX EX`, остальные ждут готовый результат (до 2 с).
  Блокировка снимается Lua-скриптом «удалить, только если она моя». Кэшируется и «не найдено» (null).
- **В кэше ключ картинки, а не ссылка:** presigned URL строится при ответе, поэтому в кэше не лежат истёкшие ссылки.
- **Redis недоступен:** отвечаем из БД (fail-open), ошибка пишется в лог.
- **Деньги:** целые копейки; `CHECK (stock >= 0)` и `CHECK (price_kopecks >= 0)` на уровне БД.

## Почему так
- **Elasticsearch для каталога** избыточен: он уже занят логами, а Postgres справляется на данных такого размера.
- **OFFSET** на глубоких страницах читает и отбрасывает все предыдущие строки, а новые товары между запросами
  создают дубли и пропуски. Keyset стоит одинаково на любой странице.
- **Версия вместо точечного удаления ключей:** товар входит в карточку и в неизвестное число страниц списков;
  найти и удалить их все ненадёжно, а смена номера версии делает это одним действием.

## Компромиссы
- Любое изменение товара сбрасывает весь кэш каталога. Для магазина с редкими правками это приемлемо; при частых
  изменениях остатков (заказы, этап 5) версию лучше делить по областям или не кэшировать остаток.
- Короткий запрос (< 3 символов) ничего не находит: триграммы работают от трёх символов.
- Для частого префикса (много совпадений) планировщик справедливо идёт по первичному ключу и останавливается после
  `LIMIT`, индекс выигрывает на редких запросах (см. замеры в README).
