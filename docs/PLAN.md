# PLAN.md — план реализации «ForsunkiShop»

Принцип: **вертикальные срезы**. Сначала тонкий рабочий путь «регистрация → заказ → оплата в заглушке», затем наращиваем. Каждый этап даёт работающий результат, тесты и PR. Правила проекта: `CLAUDE.md`.

Статус: ☐ не начат, ◐ в работе, ☑ готов.

## Компоненты

`api` (бэкенд, модульный монолит), `worker` (тот же образ), `web` (сайт, BFF), `payment_stub` (заглушка платежей), PostgreSQL, Redis, RabbitMQ, Fluent Bit + Elasticsearch + S3 (RustFS в dev) + Kibana, Prometheus + Grafana, nginx.

Compose-профили: `core` (по умолчанию), `logging`, `monitoring`, `tracing`.

## Принятые решения (согласованы с автором)

- **S3 в dev: RustFS вместо MinIO** (решение этапа 3). Официальные образы MinIO сняты с публикации (`minio/minio` на Docker Hub не существует, quay.io требует авторизации). RustFS (Apache 2.0, образ `rustfs/rustfs:1.0.4`) даёт тот же S3 API и веб-консоль; код приложения от этого не зависит.

- **Среда:** код лежит в `D:\Opencode_proj\ForsunkiShop`, запуск `make`/Docker через WSL. Репозиторий: `github.com/Stepan1709/forsunki-shop`.
- **Язык:** README, ADR, комментарии на русском; английскую версию README добавим позже. Комментарии пишем в ключевых местах и объясняем «зачем».
- **CI откладывается:** пока всё локально (`make lint`, `make test`, `make e2e`). GitHub Actions подключаем в этапе 12, когда проект стабилен.
- **Prod без VPS и домена:** проверяем `compose.prod.yml` локально с самоподписанным TLS. Деплой по SSH описываем и пишем, но реальный запуск не обязателен.
- **Mailpit** вместо MailHog (MailHog не поддерживается).
- **Поиск каталога:** Postgres `pg_trgm` + GIN, Elasticsearch только для логов.
- **Refresh-токены:** в БД хэшем, с ротацией и обнаружением повторного использования.
- **Деньги:** целые числа в копейках, валюта RUB. Заказы и платежи имеют UUID.
- **Поздняя оплата** (после `EXPIRED`): заказ остаётся `EXPIRED`, платёж фиксируется и получает `REFUND_REQUIRED`.
- **`PAYMENT_FAILED`:** терминальный статус, резерв возвращается.
- **Дополнения сверх исходного плана:** OpenTelemetry-трассировка (этап 10), Hypothesis на машину состояний (этап 5), coverage с порогом и бейджами (этапы 0 и 12), картинки товаров в RustFS/S3 (этап 3), Mermaid-диаграмма в README (этап 0, обновляется по этапам).
- **Позже:** отдельная страница управления товарами для автора (цены, описания, новые товары). Основа — SQLAdmin из этапа 3, свой интерфейс в `web` добавим после этапа 8, если SQLAdmin не хватит.

## Этап 0. Каркас ☑

**Задачи**
- Репозиторий, структура папок, `CLAUDE.md`, README, `.gitignore`, `.dockerignore`, `.env.example`, pre-commit (ruff, gitleaks).
- `deploy/compose.yml`: Postgres, Redis, RabbitMQ с healthchecks; `compose.dev.yml`: Adminer, Mailpit.
- Первая версия диаграммы архитектуры (Mermaid) в README; настройка coverage в pytest (порог включим в CI).
- Схема секретов: `make secrets`, Compose `secrets:`, чтение `*_FILE`.
- Шаблон Dockerfile (multi-stage, не root, exec-CMD, healthcheck).
- Выбор менеджера пакетов (uv), настройка Ruff, mypy, pytest. `Makefile`.
- `git init`, remote `origin`, ветка `main`, первый коммит (CI пока не делаем, см. «Принятые решения»).

**Готово, когда:** `make secrets && make up` поднимает Postgres, Redis, RabbitMQ; все healthchecks зелёные; в репозитории нет секретов; `make lint` и `make test` проходят локально.

## Этап 1. Инфраструктурное ядро `api` ☑

**Задачи**
- FastAPI-приложение, pydantic-settings, `lifespan`: engine + sessionmaker, Redis-пул, соединение aio-pika, httpx-клиент. Доступ через `Depends`.
- Структурированное логирование (structlog, JSON), middleware `correlation_id`.
- `/health/live`, `/health/ready`, единый формат ошибок (Problem Details).
- Alembic, контейнер миграций, базовые модели.
- Dockerfile и сервис в compose; graceful shutdown.

**Готово, когда:** `docker stop api` завершает приложение за секунды без потерянных запросов (проверено тестом/скриптом); `/health/ready` падает при недоступной БД; логи в JSON с `correlation_id`.

## Этап 2. Пользователи и авторизация ☑

**Задачи**
- Регистрация, логин, Argon2, JWT (access + refresh), роли (покупатель, admin).
- Rate limiting входа и регистрации на Redis.
- Событие `user.registered` (через outbox, когда он появится в этапе 4; пока можно заглушкой).
- Тесты: уникальность email, неверный пароль, лимит попыток.

**Готово, когда:** пользователь регистрируется и входит через API; лимит попыток работает; пароли хранятся только в виде Argon2.

## Этап 3. Каталог форсунок и Redis-кэш ☑

**Задачи**
- Модели: производитель, форсунка (артикул, тип, состояние, цена, остаток), применимость к двигателям.
- Список с пагинацией (cursor), фильтры, поиск по артикулу/применимости. Индексы; один запрос с `EXPLAIN ANALYZE` описать в README.
- Cache-aside в Redis, версия ключей, инвалидация, защита от stampede.
- Сидирование реалистичных данных (скрипт).
- Картинки товаров: загрузка в S3 (RustFS в dev) через aioboto3, в БД хранится ключ объекта; отдача через presigned URL или прокси `api`.
- Админка (SQLAdmin) для управления товарами (цены, описания, новые товары, картинки).

**Готово, когда:** каталог быстро отдаёт список и карточки; повторный запрос идёт из кэша (видно в метриках/логах); изменение товара сбрасывает кэш; замер «до/после кэша» записан.

## Этап 4. Обмен сообщениями и outbox ☑

**Задачи**
- `core/messaging`: подключение, объявление топологии, publisher (confirms, `mandatory`), базовый consumer, классификация ошибок, retry с backoff через TTL-очереди, DLQ с причиной.
- Outbox (модель, запись, relay) и inbox (`processed_messages`).
- Точка входа воркера, graceful shutdown.
- Тесты на реальном RabbitMQ и Postgres.

**Готово, когда:** тесты подтверждают: успех → ack; временная ошибка → N повторов → DLQ; постоянная ошибка → сразу DLQ; убитый воркер → сообщение обработано другим; дубль отсечён inbox; relay переживает перезапуск.

## Этап 5. Корзина и заказы ☑

**Задачи**
- Корзина (добавить, изменить, удалить, очистить), цены фиксируются при оформлении.
- `POST /orders` с `Idempotency-Key`: заказ `PENDING_PAYMENT` + резерв остатков (условный UPDATE) + запись в outbox, всё в одной транзакции.
- Машина состояний заказа, таблица допустимых переходов; property-based тесты (Hypothesis): из любой последовательности событий заказ не попадает в недопустимый статус, остатки не уходят в минус.
- История заказов пользователя, защита от IDOR.

**Готово, когда:** повторный `POST /orders` с тем же ключом возвращает тот же заказ; параллельные заказы на последний остаток не уводят остаток в минус; чужие заказы недоступны.

## Этап 6. Оплата (заглушка) и защита от двойной оплаты ☐

**Задачи**
- Интерфейс `PaymentGateway`, `StubPaymentGateway`, сервис `payment_stub` (создание платежа, страница «Оплатить / Отклонить», подписанный webhook).
- Воркер создаёт платёж по `order.created`; таблица `payments`.
- `POST /payments/webhook`: проверка HMAC, суммы и валюты, дедупликация по `provider_event_id`, условный UPDATE `PENDING_PAYMENT → PAID`.
- Отложенное истечение: сообщение `order.expire` (TTL + DLX), неоплаченный заказ → `EXPIRED`, остатки возвращаются.
- События `order.paid`, `order.expired` через outbox.

**Готово, когда:** тесты доказывают: двойной webhook учитывает оплату один раз; неверная подпись отклоняется; оплата после истечения обрабатывается корректно; истечение возвращает остатки; смена заглушки на другой `PaymentGateway` не требует правок бизнес-кода.

## Этап 7. Уведомления и заявки на ремонт ☐

**Задачи**
- Воркер: письма по `user.registered`, `order.paid`, `order.expired` (SMTP в Mailpit, шаблоны).
- Заявка на ремонт: `POST /repair-requests` (rate limit), сохранение, событие `repair.requested`, письмо мастеру/админу.
- Идемпотентность: одно письмо на событие.

**Готово, когда:** письма видны в MailHog; повторная доставка события не создаёт второе письмо.

## Этап 8. Сайт `web` ☐

**Задачи**
- Каркас: Jinja2, HTMX, Alpine.js, Tailwind (standalone CLI), базовый шаблон, адаптивная вёрстка, единый стиль.
- Клиент `api` на httpx (общий `AsyncClient` из lifespan), сессии в Redis (BFF), CSRF.
- Страницы: главная, магазин (список с фильтрами и поиском, карточка), ремонт (цены, контакты, форма заявки), корзина, оформление и статус оплаты, профиль с историей заказов, вход/регистрация.
- Состояния загрузки, пустые состояния, понятные ошибки, страницы 404/500.
- Dockerfile со сборкой CSS отдельной стадией.

**Готово, когда:** весь путь «зашёл на главную → выбрал форсунку → корзина → заказ → оплата в заглушке → заказ в истории» проходится в браузере; в cookie только id сессии.

## Этап 9. Логи: Fluent Bit → Elasticsearch + S3 → Kibana ☐

**Задачи**
- Ротация Docker-логов (`max-size`, `max-file`) на всех контейнерах.
- Fluent Bit (профиль `logging`): парсинг JSON-логов, отправка в Elasticsearch (индекс на день, ILM на удаление) и в S3/RustFS (gzip, префиксы по сервису и дате, lifecycle).
- Kibana: data view, сохранённый дашборд (ошибки по сервисам, медленные запросы, поиск по `correlation_id`).
- Документация: как найти путь одного заказа по `correlation_id` через `web`, `api`, `worker`.

**Готово, когда:** `make up-full` поднимает стек; логи видны в Kibana и лежат в бакете; ротация и retention настроены и описаны; по `correlation_id` находится вся цепочка запроса.

## Этап 10. Метрики и трассировка ☐

**Задачи**
- `/metrics` в `api`, `web`, воркере: RPS, ошибки, latency, длина очередей и DLQ (плагин `rabbitmq_prometheus`), заказы по статусам, hit ratio кэша.
- Prometheus + Grafana (профиль `monitoring`), дашборд в репозитории, алерт-правило на рост DLQ.
- OpenTelemetry (профиль `tracing`, Jaeger): трассы `web → api → RabbitMQ → worker`, контекст передаётся в заголовках сообщений; `trace_id` добавляется в логи рядом с `correlation_id`.

**Готово, когда:** дашборд показывает живые метрики во время e2e-сценария; в Jaeger видна одна сквозная трасса оформления и оплаты заказа.

**Готово, когда:** при всех сбоях оплата и остатки учитываются ровно один раз, сообщения не теряются, результаты задокументированы цифрами.

## Этап 12. CI/CD и prod ☐

**Задачи**
- Подключаем GitHub Actions (откладывалось до стабильного проекта). Порог coverage в CI, бейджи (CI, coverage) в README.
- `ci.yml`: ruff + mypy → unit → интеграционные (Testcontainers) → сборка образов (BuildKit cache, build-secrets) → e2e в compose → сканирование образов (Trivy).
- `release.yml`: публикация образов в GHCR по тегу/merge в `main`, деплой на VPS по SSH (`docker compose pull && up -d`), откат на предыдущий тег.
- `compose.prod.yml`: образы по тегу, секреты из файлов на сервере, без лишних портов, read-only FS, лимиты ресурсов, одноразовый контейнер миграций.
- nginx + TLS (локально самоподписанный сертификат; конфиг под Let's Encrypt готовим для будущего домена), Kibana за аутентификацией.
- Бэкап Postgres по расписанию в S3 и проверенное восстановление. Dependabot.

**Готово, когда:** merge в `main` собирает и выкатывает релиз; откат одной командой; сайт доступен по HTTPS; бэкап восстанавливается.

## Что ценно для резюме и собеседований

- Заказ и платёж: статусная машина, условный UPDATE, идемпотентность на всех уровнях, outbox/inbox, отложенное истечение заказов.
- Асинхронный бэкенд по стандартам: lifespan-ресурсы, пулы, graceful shutdown, health/readiness.
- Redis с понятной ролью (кэш, сессии, rate limiting) и измеренным эффектом.
- Наблюдаемость: JSON-логи, ELK + S3, метрики, сквозной `correlation_id`.
- Воспроизводимость: `make up`, секреты по стандартам, CI с интеграционными тестами, автодеплой.
- Цифры из этапов 3 и 11 и рассказ для каждого этапа: задача → решение → сложное место → результат → что бы сделали иначе.
